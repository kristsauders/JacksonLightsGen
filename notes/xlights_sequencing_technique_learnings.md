From building the first custom-generated sequence (Gooey, CloZee & LSDREAM, 2026-08-09). See [[xlights_show_setup]] for where the scripts live.

**Physical layout from XML, not a screenshot.** `xlights_rgbeffects.xml` model elements carry `WorldPosX/Y/Z` attributes — real 3D layout-preview coordinates. `extract_layout.py` reads these for every model and derives: (a) chase-ready families by stripping trailing numbers off names (`Orb-1..10`, `Arch 1..4`, `Tunnel Arches 1..80`, etc.) and sorting each family along whichever axis (x/y/z) has the greatest spread; (b) whole-display left-to-right / top-to-bottom sweep order; (c) side clusters (Front/North/South/Garage/Tunnel) by keyword. This made the requested screenshot unnecessary and should be the default move next time too — only ask for a screenshot if the auto-detected groupings look wrong once previewed.

**Melody/arpeggio detection: chroma beat pyin, decisively.** First attempt used `librosa.pyin` (monophonic pitch tracking) on the demucs "other" stem — it only found voiced pitch in ~18% of frames on real synth/pad material and produced zero usable arpeggio runs. Switched to `librosa.feature.chroma_cqt` (works on polyphonic/synthetic audio) with a dominance-ratio check (top chroma bin must beat the runner-up by >=1.25x to count as "clearly tonal," else the onset is treated as ambiguous/percussive and skipped) and fuzzy cycle-matching (tolerate up to 1 mismatched note per repeat, since real audio has passing tones/octave noise) — that found 8 genuine repeating patterns. **Use chroma, not pyin, for anything past a clean solo instrument.**

**Onset over-detection needs merging.** Raw `onset_detect` on a busy stem fires far more often than there are actual distinct notes (~80 onsets in 15s of an EDM "other" stem). Merge onsets closer than ~90ms before doing anything pitch-related, or the note sequence is mostly noise.

**Riser detection: relative rise, not absolute Hz/sec slope.** An absolute spectral-centroid-gradient threshold (Hz/sec) needed re-tuning per song and produced zero hits on the first pass. A relative "current peak >= 1.35x the local base, sustained 0.7-8s" walk was far more robust and portable across songs. Even so, on a dense bass-music track this still overshoots — 154 raw candidates before filtering. **Post-filter to the strongest ones** (e.g. `rise_ratio >= 1.6 and duration >= 1.0s`) before turning each into a whole-display sweep, or the show ends up with a sweep every 4-8 seconds, which reads as noise instead of a special moment. This threshold is a per-song tuning knob, not a universal constant — expect to adjust it after the first preview of every new song.

**Bandwidth distinguishes riser character.** Mean spectral bandwidth during the rise (`>2200-2500 Hz` = broadband/noisy, else tonal) cleanly separates "pitched synth riser" (map to a vertical bottom-to-top sweep) from "white-noise filter sweep" (map to a horizontal whole-display sweep) — this held up well and is worth reusing as-is.

**Pre-drop implosion detection worked well on the first pass.** Simple: find brief (0.1-2.5s) dips below ~12% of peak RMS, check if a big jump (>=55% of peak) follows within 3s. Found 12 genuine cutout-then-slam moments on Gooey with no retuning needed.

**Cymbal/hihat accents: a highpass + onset_detect is enough.** 4th-order Butterworth highpass at 6kHz on the drums stem, then standard onset detection, found 483 accent candidates (thin these — used every 3rd, and only in high-energy sections — or it's overwhelming).

**Effect-placement architecture that worked:** keep the proven ambient 3-layer bed (layer 0 background wash, layer 1 motion, layer 2 accents — reused straight from `engine.py`) running under everything so nothing is ever dark, then add a dedicated top layer (layer 3) purely for signature cues (arpeggio chases, riser sweeps, implosions, cymbal sparkle) so they don't fight the ambient effects for the same layer slot. One exception: Single Line models (verticals/C9/window strands) had their layer-1 motion *skipped* entirely in the ambient pass and replaced with a dedicated per-beat bounce chase (`Chase_bounce`/"Bounce from Left" SingleStrand effect) — putting a second competing chase direction on the same layer looked muddy in testing/reasoning, so exclude-and-replace beat cleaner than layering on top for that one category.

**Cross-model chase is the core reusable primitive.** Nearly every "opportunity" the user described (arpeggio following a melody across props, a wave sweeping across the display, verticals swaying together) reduces to the same operation: take an ordered list of models and a list of timestamps, and give each model a brief `On` burst (fade in ~0.03-0.08s, fade out ~0.1-0.25s) at its turn. This is the xLights community's "leaping arches" technique generalized to arbitrary prop families — validated via the effects manual and community threads before use. Don't reach for a per-model "Wave" effect for cross-prop sway (parameter key names for it weren't verified against a real xLights XML and guessing wrong internal `E_` keys risks a silently-broken effect) — the cross-model burst-chase achieves the same visual read using only already-validated effect keys.

**Real bug found and fixed (2026-08-09): section-detection coverage gaps caused "dead"/frozen lighting stretches.** `structure.py`'s `detect_structure()` built its section list by iterating boundary pairs and doing `if end - start < 1.0: continue` to skip short segments — but `continue` just drops that segment from the output list entirely rather than merging it into a neighbor, leaving a real gap in time with **zero** `SongSection` coverage. Both `engine.py`'s built-in auto-generation *and* my custom generator only place ambient-bed effects within a section's span, so any coverage gap = zero effects = the lights visually freeze/go dark for that whole stretch while the music keeps playing. On Gooey this added up to 18 gaps totaling **47 seconds (~20% of the song)** with no bed coverage at all — including one right at the first drop (~4.9s), which is exactly what read to Krists as "the lights are off by multiple seconds." Root cause was almost certainly the arrhythmic spoken-word intro confusing the self-similarity-based boundary detector into planting boundaries close together. **Fixed at the source** in `structure.py`: after dedup, merge any boundary closer than 1.0s to the previous kept boundary (extending the segment) instead of just filtering the resulting pair — guarantees contiguous, gap-free section coverage for every song, not just Gooey. Confirmed fix: 0 gaps post-patch, and section resolution near the intro actually improved (57 sections vs. 20). **When debugging "sync feels off" complaints in future songs, check `analysis['sections']` for coverage gaps first** — it's a cheap, high-signal check (`sections[i+1].start_time - sections[i].end_time`) before assuming the detection *times* themselves are wrong.

**Second debugging round (2026-08-09, same day): three more real bugs found by systematically comparing against a real finished sequence + audio analysis, in response to "rhythms don't seem aligned."** Don't skip this kind of investigation next time a sequence "feels off" — every one of these was a genuine bug, not a taste/tuning issue, and none were guessable without measuring:

1. **Demucs output lags the original mix by ~552 samples (25ms) @ 22050Hz** — measured via cross-correlation between the original mix and the sum of the 4 separated stems, consistent to the sample across early/mid/late points in the song (correlation ~0.99 at the true lag vs. ~0.2 at zero lag — a *huge* difference, this is not noise). Every timestamp computed from a stem (onset times, energy curves) needs this subtracted before use. Fixed at the source in `analyzer.py` (`DEMUCS_OUTPUT_DELAY_SEC`, applied in `analyze_stems()`) and mirrored in `custom_tools/detect_cues.py` (`STEM_DELAY_SEC`) since it does its own independent stem-based detection outside the shared analyzer. **On its own this is too small (25ms) to explain a "seconds off" complaint** — don't stop here thinking it's the whole story.

2. **`engine.py`'s Chase effect presets used the wrong xLights parameter key** — `E_SLIDER_Chase_Rotations` instead of the real `E_TEXTCTRL_Chase_Rotations` (discovered by diffing against the actual settings string of a real production effect). xLights silently ignores unrecognized keys and falls back to its own default, so this setting had probably never actually taken effect in any auto-generated sequence — chases only ever did xLights' default rotation count regardless of what the preset dict said. **When adding a new effect parameter, always verify the key name against a real `.xsq`'s `EffectDB` entries, not just the effect's UI description** — a wrong key doesn't error, it just silently no-ops.

3. **Chase/rotation-count effects need duration- and tempo-scaled rotation values, and the baseline value engine.py used (a flat `"1"`) was far too low.** Measured directly from a real finished sequence (Cold Heart PNAU Remix, tempo 117.45 BPM): the "Arches" group's layer-1 SingleStrand chase used `Chase_Rotations=8` over an 8.275s block — i.e. **about 1 full rotation every 2 beats**, not 1 rotation per multi-second block. A block-duration-agnostic `rotations="1"` (what every Chase preset had) means a chase spanning a whole bar (or more) only sweeps once across the *entire* span, which reads as a slow single pass rather than a rhythmic pulse — this is very likely the dominant cause of "the rhythms don't feel aligned with the beat," more so than any of the pure timing-offset bugs. Fixed with a `scale_rotations()` helper in `generate_gooey.py` that computes `rotations = round(block_duration_sec / (beat_sec * 2))` and overrides the settings dict at placement time (`EFFECT_VARIANTS` itself stays a static preset table, so this has to happen at the call site, not in the table). **Reuse `scale_rotations()` unchanged for every future song** — the ~1-rotation-per-2-beats target is measured from a real example, not guessed, and block duration/tempo are the only inputs it needs.

4. **`LightModel.model_category` (in `models.py`) silently bucketed 70 models (30% of the show) into the generic `"other"` category** — every `Matrix` (42: curtains, window matrices, floods, orbs), `Icicles` (12), `Star`/`Sphere`/`Circle` (15) model fell through because the property only explicitly checked for `arch`/`tree`/`single line`/`poly line`/`window`/`custom`. `"other"`'s effect pool is thin (`ColorWash_slow`/`Twinkle_ambient` for bed, a chase effect not well-suited to 2D grids for motion) — this is exactly why matrices/curtains looked like "just colors fading." Fixed by adding explicit `matrix` and `icicle` categories (mapping `star`/`sphere`/`circle` to the existing `custom` bucket, which already suits individual decorative shapes), plus matching entries in `engine.py`'s `BED_EFFECTS`/`MOTION_EFFECTS`/`ACCENT_EFFECTS`/`STEM_MOTION_OVERRIDES`. **After this fix, check `Counter(m.model_category for m in show_config.models)` against `Counter(m.display_as for m in ...)` for any new show/layout** — any `display_as` value not explicitly handled silently lands in `"other"` and gets the thin default treatment. This is a one-line-per-type check worth running whenever a show's model list changes.

5. **xLights effects can be natively music-reactive, and real sequences lean on this.** The real "Orbs" (Matrix) effect in the reference sequence used `Tendril` with `E_CHOICE_Tendril_Movement=Music Circle` — its motion is driven live from the audio by xLights itself at render/playback time, not from manually-computed timestamps at all. Copied that exact validated settings string into `engine.py` as the `Tendril_music` preset (safe reuse, zero guessed keys) and made it the primary `matrix`-category effect. **Worth investigating further next time**: other effects likely have similar `UseMusic`/reactive toggles (e.g. `Meteors` already has `E_CHECKBOX_Meteors_UseMusic`, currently always set to `"0"`/off in our presets) — leaning on xLights' own audio-reactivity for more effect types could reduce how much manual beat-timing is needed at all, and is worth a dedicated investigation before the next song.

**Third debugging round (2026-08-09, same day): the biggest lever yet — real xLights model groups existed the whole time but the parser silently returned zero.** Prompted by feedback that curtains render as separate panels instead of one canvas, orbs/floods sparkle randomly instead of flowing, and arches don't sweep side to side.

1. **`load_model_groups()` in `show.py` was reading the wrong XML location.** Model groups live in their own top-level `<modelGroups>` element (a sibling of `<models>`), not nested inside `<models>` — the old code searched inside `<models>` and always got zero, silently. This show actually has **204 real, human-curated groups** (`Arches`, `Orbs`, `Floods`, `Curtains All`, `C9s`, `Window Matrices`, `Tunnel`, etc.) that had never once been used by any auto-generated sequence. **This is probably the single biggest lever for "feels like one cohesive show" vs. "feels like isolated props"** — always verify `len(show_config.model_groups) > 0` for any new/copied show folder before assuming zero groups means the layout genuinely has none; check the raw XML for `<modelGroup` tags directly if in doubt, don't trust the parsed result alone.
2. **A group's `models=` list can reference other *group* names, not just leaf models** (e.g. `"Arches GRP"` → `"Arches"` → `"Arch 1,Arch 2,Arch 3,Arch 4"`). Needed recursive resolution down to real model names (`resolve()` in `show.py`, with cycle protection via a `seen` set and silent-skip for stale references that resolve to neither a model nor a group).
3. **Groups overlap heavily and hierarchically** (`Arches` ⊂ `ALL Roof` ⊂ `ALL House` ⊂ `ALL Display`), and the original group-consuming code in `engine.py`'s `_detect_model_groups` didn't dedupe between groups at all — every group got used independently, so a model belonging to 3 overlapping groups got its ambient effects placed 3 times over. Fixed by processing groups **smallest-first** and skipping already-claimed models, so each model lands in exactly the most specific group it belongs to. This alone cut the ambient effect count by ~10% and was very likely a real contributor to "too dense."
4. **A show's own groups can be stale relative to its current physical layout** — this show's groups still reference a single legacy `Curtain Garage` model that was since physically replaced by 5 real panels (`Curtain Garage 1` through `Curtain Garage-5`), and no group was ever updated to include them. Consequence: with real xLights groups now used, the old prefix-based auto-detection (which *did* correctly find those 5 panels) stopped running entirely, since the code returned early the moment any real groups existed — so the 5 real panels silently fell through to fully individual treatment, reproducing the exact "renders as separate panels" bug via a new mechanism. **Fixed by combining strategies**: run real-xLights-group detection first, then run prefix-detection *only on whatever's left uncovered*, and merge both results. Don't let one grouping strategy fully disable the other — always check what a "successful" strategy left on the table.
5. **Uniform per-group effects still look flat even with correct grouping.** Giving every member of a group the *same* effect at the *same* time (which is what both grouping strategies did before this round) reads as a synchronized wash, not a continuous canvas — it's not the same as one flowing pattern across the physical array. Added `cross_model_cascade()`: spatially-orders a group's members (reusing the WorldPosX/Y/Z trick — sort by whichever axis has the most spread among just those members) and gives each one a brief staggered burst across the block's duration, alternating direction every bar for a bounce feel. Used this as the **default** motion behavior (not just a rare signature moment) for any `matrix`/`arch` category group with 4+ members — this is what actually produces "arches sweep side to side" and "curtains read as one moving surface" rather than N independent copies of the same effect.
6. **The high-energy bed override had a category-blind bug**: `bed_key = "Twinkle_dense" if "Twinkle_ambient" in bed_choices else bed_choices[0]` fired for *any* category whose pool merely contained `Twinkle_ambient` — which silently overrode the new `Tendril_music` pick for `matrix` models during every high-energy section (a large fraction of any song's runtime), which is exactly why orbs/floods read as "constant sparkle/strobe" rather than the intended coherent motion. Needed an explicit category check to actually let the better pick win.
7. **Floods (and similar single-purpose accent props) shouldn't be part of the constantly-running ambient bed at all.** Per feedback, floods are best as *rare, punchy, rhythmic* moments (L-R-L or T-B-T sweeps), not a prop that's always doing something. Excluded the `Floods` group from the generic ambient pass entirely and gave it a dedicated sparse pass: only in high-energy sections, only every other bar, alternating sweep direction. **Neighbor-dimming when a flood fires (an explicit ask -- "floods work best when the other models near that flood are off") is not yet implemented** — flagged as a real gap, not solved by anything above; worth a dedicated pass next time rather than a partial/rushed attempt.

**Fourth round (2026-08-09): the whole per-model architecture was wrong — see [[xlights_human_sequence_patterns]] for the replacement spec.** Feedback was that curtains still duplicated rather than spanned, matrices/tunnel/trees showed only basic fades, arches moved too fast, sections felt same-y, and everything was still on all the time. Rather than patch again, I measured four of Krists's finished sequences and found the generator was the wrong *shape*, not just mistuned: humans target ~50 GROUP elements with sparse staging (11-26% lit) and short effects (median ~500ms), while the generator targeted all 235 models wall-to-wall with section-length beds and 43k placements. Rebuilt as `custom_tools/generate_song.py`. Specific corrections worth remembering:
- **`B_CHOICE_BufferStyle` was the literal "duplicated vs spanning" bug** — `Per Model *` repeats an effect on every group member; `Per Preview` spans the group as one canvas; `As Pixel` makes each model one pixel (the native way to do cross-prop chases, better than my hand-rolled staggered-burst helper). `engine.py`'s stock presets hardcode `Per Model Single Line`.
- **This layout has overlapping container/panel model pairs** (`Curtain Garage` container vs `Curtain Garage 1..5` panels). Target containers, never both levels. Detect containers as: empty `Controller` + `NumStrings > 1`.
- **I had the rotation lesson backwards.** Round 3 concluded "scale rotations up with block duration" from a single Cold Heart layer using `Rotations=8`. Across all four sequences, chases overwhelmingly use `Rotations=1.0` with *short* effects — rhythm comes from many brief one-rotation effects on beats, not long effects spinning fast. My `scale_rotations()` helper is what made the arches look like fast blur; it's gone. **Beware generalizing from a single measurement.**
- **Effect-mix balance needs checking, not just effect choice.** First rebuild attempt was 82% `On` bursts (monotonous flashing) because the pulse role was over-weighted; rebalancing toward feature/motion (38% of active targets) brought `SingleStrand` from 80 → 1171 placements and matched the chase-dominated human vocabulary.
- **Guard centerpiece props explicitly.** Small incidental groups can absorb a hero prop and leave it with nothing of its own — the Mega Tree ended up with zero effects because `Mega Tree GRP` (Mega Tree + the distant Tunnel Matrix) claimed it first. A `HERO_MODELS` set claiming slots before groups fixes it. Cross-check by listing per-target effect counts after generating.
- **Big 2D canvases deserve a different effect pool than small props** — Mega Tree, Garage Roof, Sun Room Window Matrix, Tunnel Matrix and the curtains now draw from Spirals/Pinwheel/Galaxy/Curtain/Ripple/Butterfly instead of washes.
- **`Off` is an effect**, used explicitly by human sequencers to force darkness (e.g. holding black between a pre-drop implosion and the drop hit). Absence of effects is not the same as a committed blackout.
- **Still open / not yet done**: flood neighbour-dimming (dim props physically near a flood when it fires); using more of xLights' native music-reactive effect toggles (`Meteors_UseMusic`, `Strobe_Music`, VU-meter-style effects) instead of hand-timing everything; `Shader` effects (used heavily in Silent Night, needs external shader files).

**Fifth round (2026-08-09, v7): submodels, a miswired model, and cast-size discipline.** Detailed in [[xlights_human_sequence_patterns]] (kept there since it's all measured-spec material) — summary only here: (1) submodels (`Parent/SubName` addressing, e.g. window-outline verticals/horizontals, snowflake spokes/arms/rings) were a whole addressable layer silently dropped by two separate parser bugs, now fixed; (2) `Curtain Garage` looks like a valid spanning container but its `StartChannel` is wired to the *front* curtain's controller — a real data bug in the show file, flagged to Krists rather than silently worked around; (3) never place an effect on a synthetic/fallback group name directly, broadcast to its real members, or it either orphans or silently aliases onto an unrelated real model; (4) cast pool size needs its own cap independent of per-section activity, because rotation-over-a-whole-song is a separate density axis from simultaneous density; (5) confirmed twice now, not once: don't subdivide a motion effect's update rate to add energy during hot sections, it reads as strobe both times it was tried — light more targets instead.

**Round 17 (2026-08-11): "shaders not tied to the beat" — three rounds of fixing the wrong thing, then a measurement that settled it.** Krists said this three separate times; each earlier attempt worked on *when a shader starts and stops* (bar-quantised change marks, A/B sway variants flipping every 2-4 bars). Both were real and neither was visible, because between boundaries a shader is a continuous wash and 4 bars is ~8 seconds — nothing happens ON the beat for a viewer to lock onto.

- **The fix is a per-beat brightness value curve, and it's Krists's own technique.** Grepping his finished `.xsq` files for `VALUECURVE` turned up a hand-drawn 5-cycle pulse: `C_VALUECURVE_Brightness=Active=TRUE|Id=ID_VALUECURVE_Brightness|Type=Custom|Min=0.00|Max=400.00|RV=TRUE|Values=0.00:0.67;0.09:0.39;0.20:0.67;...`. Semantics: `t:v` pairs, **t normalised 0-1 across the effect's own span**, **v normalised 0-1 of the Min..Max range** (so with Max=400, v=0.25 is plain 100% brightness). Points must be strictly increasing or xLights silently ignores the curve and renders full brightness. `beat_pulse_palette()` in `generate_song.py` builds these from the **real detected beat times**, so the pulse follows tempo drift instead of approximating it with a sine.
- **Value curves for the Color panel live in the PALETTE string, not the effect settings string.** They appear right before `</ColorPalette>`. Same is presumably true for hue/saturation curves.
- **Latent writer bug this exposed:** `xsq_writer.py` built its `<ColorPalettes>` list from `spec.palettes` only, and any effect whose palette wasn't in that list hit a bare `except ValueError: pass` — the effect still rendered, **in the wrong colours, with no error anywhere**. Any per-effect palette variant was impossible until fixed. Now the palette list is built from `spec.palettes` **plus every palette an effect actually uses**.
- **Measure beat-lock objectively, don't eyeball it.** Ratio of mean prop brightness within ±60ms of a detected beat vs. off-beat frames; 1.00 = no relationship. On Gooey this immediately showed the first version only worked where I'd gated it: Mega Tree (Shader) 1.44, but Sun Room Matrix and Garage Roof 0.98 — they were running **Plasma**, a built-in with exactly the same wash defect. Widening the rule from "the Shader effect" to "anything placed as a multi-bar hold" took them to 1.16/1.14. **The rule should be the placement, not the effect name.**
- **Shader speed was tempo-blind.** Every song ran shaders at a fixed base 400 whether it was 86 BPM or 143. Now scaled `400 * clamp(tempo/120, 0.6, 1.5)`, read at module import from the head of `analysis.json` (`_peek_tempo()`, since `register_shaders()` runs before the full analysis is parsed).

**Round 17, second finding: an "always-on" layer that was silently off for half the songs.** The four-on-the-floor pulse layer was gated behind `kick_persistent` (kick present on ≥80% of beats). Measured across 8 songs: 4 failed it (Gooey 59%, The Ambition 64%, World Is Mine 66%, Fara 78%) and therefore had **no beat-marking flash at all** — which is exactly what "there's almost nothing pulsing or flashing to the main beat" meant. Krists also asked "do we need better stem separation?" — measured and answered **no**: kick onsets were found on every song (172-520 each). **When a feature is reported missing, check whether a gate turned the whole layer off before touching detection quality.** Replaced with an always-on accent that rotates one prop per kick (three spread props on downbeats), drawn from a pool excluding floods and low-prominence sub-detail groups.

**Round 18 (2026-08-11): "an effect placed correctly is not an effect that READS."** Three separate complaints ("still not seeing kick drum flashing clearly anywhere", "the drops don't look like drops at all", "the pulsing is a little early") all turned out to be different faces of the same blind spot: the `.xsq` said the content was there, `verify_render.py` said the colours were fine, and none of it was visible.

- **A prop that is already saturated cannot flash.** Measured on World Is Mine: Orb-1 (the bass voice carrier) sits pinned at byte **255 for seconds at a stretch**, so a kick flash placed on it changes nothing. Mini Tree 1 sat at 76-78% lit through a whole chorus; a hit that went 94->166 and then STAYED at 166 is a step, not a flash. **A prop cannot mark the beat and perform another instrument at the same time** — the beat anchor must be a prop with no voice and no ensemble movement, with its ambient fill suppressed so it has darkness to come out of. After that fix, kick-pop (brightness on kick / off kick) went 1.18 -> **1.76** on the anchor.
- **Rotation is not a beat marker.** 695 flashes rotating through 9 props at 123 BPM = each prop fires **once every 4.5 seconds**. Both of Krists's asks are satisfiable at once: one ANCHOR hits every kick for a whole section (legible), the anchor changes per section (not repetitive), rotation continues underneath as travel.
- **Drop detection required a cutout, so songs that don't go quiet got NOTHING.** `detect_predrop_cutouts` needs a near-silent (<12% of peak) build. World Is Mine builds at 30-45% and produced **zero** candidates — no blackout, no hit, measured contrast 1.0x at both of its biggest moments. Added `detect_energy_drops` (sustained level STEP UP, no cutout required): found Krists's two drops at 1:36.0 and 3:38.9 first try, contrast now **3.6x and 4.0x**. The two detectors are complementary — cutout-rich songs use none of the new ones.
- **A fully deterministic `min(candidates, key=rank)` makes every song identical.** Voice->prop assignment picked the same prop for each voice on all ten songs (hats->Stars, bass->Orbs, ...), which left the same leftovers to anchor the beat on nine of ten. Fix: take the best (prominence, category) tier exactly as before, then choose **within that tier** by a per-song seed — never a worse prop, just a different equally-good one.
- **A matrix should not flash flat.** "Flashing the whole window matrix green isn't the best use of a matrix." Beat hits are now shape-aware (`beat_hit_key`): matrices/large canvases get a Shockwave ring, linear props a centre-out chase, discrete objects a flat `On`.
- **xLights rounds effect starts to the nearest render frame, so placements jitter ±half a frame.** Measured on Fara: of 262 non-frame-aligned flashes, **129 rendered a frame early and 129 a frame late**, purely on where the sub-frame remainder fell. At 40fps that is ±12.5ms of *irregular* timing, which is what reads as sloppy (a consistent offset would not). Fix: snap every placement to `FRAME_MS` in `add()` — and re-snap after any post-processing that rewrites times (blackout clipping, run-up dip truncation), which is where 322 stragglers were still coming from.

**Two measurements from this round that were WRONG — don't repeat them:**
1. **Regularizing the beat grid made alignment worse, not better.** Fara's beats wander ±195ms against a perfectly regular grid (std 67ms), which looked like tracker drift. Scored against real onsets, the raw grid is tight (|err| 26ms, std 13ms) and a locally-refitted regular grid was *worse on 4 of 5 songs*. The wander is the music's real tempo variation and the tracker is correctly following it. **Test a grid "fix" against detected onsets before shipping it.**
2. **A half-max-crossing search inside a ±120ms window reported a −120.0ms median — exactly the window edge.** The measurement was saturating on its own boundary, not measuring anything. Same class of error as the absolute-lit-threshold bug in `prop_probe.py`. **When a measured value sits exactly at a search bound, the measurement is the bug.**

Also confirmed clean this round, so don't re-investigate: sequence duration matches the mp3 to the millisecond, `mediaFile` is correct, there is no leading gap, and whole-display light-vs-audio cross-correlation peaks at **0ms** on songs where the correlation surface is unambiguous. (On strongly periodic tracks that cross-correlation aliases at ±1 beat and cannot resolve absolute lag — read the correlation values, not just the argmax.)

**Round 19 (2026-08-15/16): the custom shader library, and how to tell a good shader from a broken one.** The library is now 44 shaders, **32 written for this show**, all greyscale.

- **A greyscale shader renders GREY. It is not recoloured by the palette.** This belief was held for the whole custom library and was never tested; all 32 shaders had been painting the house white/grey. Measured on Gooey: mean saturation **0.00** on Smoke Drift, Drift Cells, Rain on Glass, Cable Knit wherever the shader was alone on the prop. Colour appeared only where another layer — or a GROUP element rendering over the same model — put it there, which is why sampling songs gave an unattributable 1-to-6 hues and looked fine. (Related: Krists once reported "multiple matrices are just white".)
- **The palette's route into a shader is an ISF `color` input**, established with probe shaders on a real render: xLights feeds `color` inputs automatically from the palette's ACTIVE colours, slots 1/2/3 in declaration order, overriding the ISF default and emitting no setting. Floats declared before them don't disturb the mapping. A slot beyond the active colours comes through white. All 32 custom shaders now declare `c1/c2/c3` plus `palcol()`/`palpos()` helpers — see `colorize_shaders.py`, which does the conversion and keeps originals in `Shaders/_greyscale_backup/`.
- **Colour must not be driven by the shader's own value alone.** Alpha carries that same value, so the dark end of the ramp is transparent and only the top of the palette is ever visible — measured as saturation rising to 0.25-0.98 while the hue count stayed stuck at **1**. Colour is now driven mostly by a slow diagonal drift (`palpos`), nudged 35% by the value. After that: 4-7 hue buckets and saturation 0.84-0.92 on every shader.
- **`ColorPalette.active_colors` holds palette SLOT NUMBERS, not per-slot flags.** `[1, 1, 1]` marks slot 1 active three times and leaves 2 and 3 off. This was in my own test harness and made every shader report a single hue, which looked exactly like a shader bug and cost a bisect. `[1, 2, 3]` is correct.
- **Stock shaders that declare colour inputs still stay out of the pool** — the old `has_uncontrolled_color` reasoning was wrong about the mechanism, but the measurement behind it was real (Zoom Loop.fs hit ~39% saturated red shared across 7 canvases). A stock shader can take a palette colour *and* mix in its own, and nothing distinguishes them statically. Shaders written for this show are exempt via their CREDIT line, since their colour comes only from c1/c2/c3.
- **Every custom shader declares a SIGNED `rate` input**, so `register_shader_sway()` can produce a genuine direction-reversal A/B pair rather than two speeds of the same thing.
- **`shader_smoke_test.py` is the gate, and it exists because reading GLSL does not work.** Three failure modes have all shipped past a careful source read: a compile error (renders the prop BLACK, silently), a shader that compiles but sits at one value (flat wash), and one that pins near white (blown-out panel that drags the song's lit fraction up). It renders every shader for 8s on Garage Roof (largest plain 2D canvas — never Fence Matrix 1, which is rotated front-to-back) and measures lit / spatial variance / motion / **flicker**. `xLights --shadertranslate` is NOT the answer: it takes a directory and reports "0 .fs found" against this show's Shaders folder.
- **The strobe test has to be whole-panel MEAN brightness frame-to-frame, not per-channel change.** Oil Film measures 0.038 per-channel and 0.010 panel-level: bands sliding fast across the canvas, completely calm to look at. A shader that dims and brightens the entire canvas every 25ms is a strobe even when each pixel moves only a little. Only the panel-level number can hurt anyone.
- **Measured effect of the colour conversion**, Gooey v119 -> v120 over the same 62 solo shader spans: mean saturation **0.08 -> 0.72**, median distinct hues **0 -> 5**. Red stayed at 0.2% mean, lit moved 54% -> 55%, beat-lock 1.12 -> 1.14. So the change is hue only, as intended — nothing else in the pipeline shifted.
- **Shaders with a focal point must be marked centred** (`CENTRED_STEMS`) or they get spread across the whole facade as one canvas — Krists saw this as "a rainbow circle across the garage roof, garage matrix, and fence matrix." Anything with a middle (blooms, flocks, metaballs, rings, spirals) belongs on one canvas at a time; only even all-over textures can be shared.
- **For "colour movement", write the shader as a clean full-range value RAMP** rather than a shape on a dark ground — Oil Film's triangle-wave interference bands are the test case. Use a triangle wave, not `fract()`, so the ramp is continuous in both directions and bands slide instead of snapping back.

**Round 20 (2026-08-16): "the matrices seem oddly aligned" -- three causes, none of them the shader.**

- **Role was leaking into the picture.** ROLE_FEATURE subdivided a section on the bar grid and gave every span a beat-locked brightness curve; ROLE_TEXTURE and ROLE_OUTLINE placed ONE flat span across the whole section with no curve. Two matrices side by side running the SAME shader therefore started and stopped at different times and only one of them breathed. Measured on Gooey: Smoke Drift 7600-13500 with a pulse on Fence Matrix 1, 7225-13500 without one on Garage Roof. Role is an internal staging concept and must never be visible as neighbouring canvases disagreeing -- everything now goes through one `hold_spans()`.
- **The run-up dip rolled its dice PER EFFECT.** At each section approach some big canvases truncated into the dip and their neighbours ran straight through. Fixed by deciding once per window for the cohort.
- **Two probabilities that look like one.** 0.66 per EFFECT is a partial thinning inside one prop's stream, which is what stops a dip reading as a mistake. The same 0.66 applied to a synchronised cohort becomes a coin flip on whether the breath happens at all -- and since the big canvases carry most of the lit area, the dip median went 0.61 -> 0.88 on ENIGMA, i.e. the breath vanished. **When a decision is moved from per-item to per-group, its probability has to be re-derived, not carried over.**
- Result on Gooey's first 45s: 12 distinct start times -> 6, every one shared by 4+ matrices, none used by a single matrix, and no mixed pulse/flat. Fara's Sun Room went 3 holds/2 pulsing -> 6/6.

**Round 20, second finding: `is_centred()` could only ever know what it had already been burned by.** A hand-maintained list of stem names missed `Wisps` -- a stock shader, not circular or radial, but with a focal point all the same -- which spanned across `ALL Display` put its centre in the empty air between props so the matrices caught only the frame's edges. Replaced with a measurement (`shader_span_test.py`): span each shader across the real layout and look at how the light lands on 202 props. Wisps leaves **63%** of props below a fifth of the brightest, against a **~39% floor** for a genuinely even texture (many props are small or at the frame edge regardless). 21 of 47 shaders fail. **Prefer measuring the failure over enumerating its causes** -- the same lesson as the shader smoke test.

**Round 20, third finding: the vocal is not a drop.** Both hole detectors work off a broadband envelope and cannot tell WHICH instrument refilled the hole. At Gooey's false drop the vocal returns at 13.7x its in-hole level while the bass comes back at 0.39x -- the band is not back, the singer is. At ENIGMA's real drop the ordering reverses (drums 32.5x, bass 2.2x, vocals 3.2x), so the test has to be RELATIVE: reject when the vocal outruns the whole rhythm section. Kept as a veto rather than a score, because a corroboration BOOST fixed one song and broke ENIGMA's double drop; a veto can only remove a moment that measurably isn't one. Checked against all 74 candidates in the library before shipping: 15 vetoed. Guard: if every one of a song's moments is vocal-led (a ballad), the strongest is put back so it still has a shape.

**Greyscale is now a PALETTE, not a shader property.** Since the shaders read c1/c2/c3 from the palette, three neutral palettes (`ash`, `bone`, `pewter`) reproduce exactly the pre-colour look. Gated to sections below the song's OWN median energy (absolute thresholds don't transfer between songs), a third of the time, never twice running -- lands at 1-12% per song.

**The "nothing custom in the house bed" rule was inverted by the colour conversion.** It was written after Slow Dawn regressed 12 to 12's red, but that red came from STOCK shaders painting their own colours across the facade. Custom shaders now take colour only from the palette, which never leads with saturated red, so they are the safer half. Keeping them out left a house-bed pool of three -- repetition in the most visible layer of the show. Reopened, gated on the span measurement; red measured 0.0% mean on all three test songs afterwards.

**Round 21 (2026-08-16): the drop-and-fade intro, and five inert fixes in a row.** Gooey's first minute is five drop/fade cycles: one isolated kick, then a long decay, repeating every 11.03s (4.82, 15.85, 26.90, 37.92, 48.97, 59.99 -- the last one the main drop where the track opens up).

- **I called this "already aligned" once and was wrong.** Four of the hits sat near a section boundary, so I concluded the sections tracked the drops -- ignoring that there were **32 section boundaries in the same 62 seconds**. Check how many boundaries DON'T correspond, not just how many do.
- **The kick detector misses hits.** It finds 4.78, 26.90, 37.87, 49.02 but not 15.85, leaving a 22s hole that looks like one long cycle. The musical figure is far more regular than the detector, so infer the PERIOD from the isolated hits and snap each predicted start to a real onset when one is within 0.5s.
- **Opportunistic claiming doesn't work in a quiet passage.** Letting "whichever section is active" own a cycle covered 1 of 5, because big canvases are rarely in the active set during an intro. Third time this project has needed a dedicated pass instead of a rule inside the section loop.
- **Then five successive attempts to shape the fade all measured 1.1x-1.8x**, whatever was changed upstream: cycle holds, a decay envelope, cutting the cast, exempting the clipping passes, extending the envelope to every prop. **The cause was my own pulse-curve rebuild pass overwriting the fade envelope with a beat pulse** -- it recovers a "depth" from any brightness curve's peak, and a hit-and-decay curve looks like a very deep pulse. Exempting the cycle holds took the same measurement from 1.2x to 3.8-7.0x, and the main drop to 32.5x out of near-darkness. **When a series of upstream fixes all fail to move a number, stop tuning upstream and look for something downstream overwriting the result.**
- **Tuple keys break across passes that rewrite times.** Exemptions keyed on (model, start, end) silently stopped matching once add() snapped times to the frame grid -- one cycle got clipped to a 75ms fragment while the others survived. Key on `id(effect)` instead.
- **A cycle start is not a drop.** In a drop-and-fade passage every cycle opens with a big hit, so the detectors stage each one as a full implosion. Only the last is the real drop ("there is a false drop before that where bass starts"). Demote candidates that coincide with a non-final cycle start.

**Round 21, other measured findings:**
- **`Chase` on a 2D matrix renders as broad vertical bars sliding sideways** -- it was the most-used effect on the big matrices by a wide margin (445 placements, 1300s across five songs, double the next entry). Removed from the flat-canvas feature pool; 20.0% -> 2.1% of matrix time.
- **A brightness value curve is stored NORMALISED across its effect's span**, so any pass that truncates an effect afterwards squeezes the whole pulse into what remains. Measured: a 1300ms Plasma still carrying a curve built for a much longer span, peaking every ~104ms = **9.6 Hz on a whole matrix**. This is the "flash/pulse the matrices too fast, it looks like strobing" report, and it is a migraine risk. Curves are now rebuilt for final spans; strobe runs on So Easy went 210 -> 18.
- **The strobe test has to be whole-prop MEAN brightness with a large swing.** A 0.10 threshold reported 20 Hz "strobes" that were just fine moving texture rippling a small prop. Real flashing takes the prop most of the way down and back: threshold 0.30, rate 4.5-12 Hz, 4+ peaks (`verify_strobe.py`).
- **The house bed can strobe SMALL props while looking calm on a matrix.** Wind Wheat's thin stalks flicker a 90-node snowflake at 10 Hz; a big matrix averages thousands of nodes and hides it. `shader_smoke_test.py` measures one large canvas by design and cannot see this.
- **Group targets never qualified as "large"**: node counts are keyed by MODEL name, so every group fell through, and the three-panel window-matrix group drew flat washes while every individual matrix ran patterns. Membership is the reliable signal. Fixing it took that trio from 197s to 693s of content, shader 12% -> 55%.
- **An anchor prop is deliberately kept plain** (its ambient fill is suppressed so the flash has darkness to come from). So "prop X looks blank" and "prop X flashes the beat" are the same fact, not two.
- **A per-section coin flip cannot guarantee a look ever appears** -- greyscale palettes gave Fara zero sections. Choose the sections outright (quietest ~20%) instead.
- **`spread_x >= 40` structurally excluded the verticals** from the long-run flash pass: they are tall, not wide, so they could only ever move.

**Round 22 (2026-08-16): a second vocabulary, for passages with no beat.** Everything in this generator assumed a beat to hang things on -- an anchor prop flashing the kick, voices mapped to props, gutter flashes, submodel stepping, leaping arches. That is right for a chorus and wrong for a drumless intro: "the lights are pulsing and being very rhythmic when they need to be more smooth and flowy."

- **`ambient_sections.py` works on PASSAGES, not sections.** The detector emits slivers -- This Version of You is 100 sections in 172s, about one per bar -- and anything planned against those makes the show restate itself every 1.1s. Adjacent sections sharing a classification are fused and the measurements recomputed over the whole span.
- **Drumless is NOT the same as quiet**, and conflating them is the main trap. This Version of You runs at 0.78-0.80 loudness with ZERO drums for 37 seconds at a stretch -- a loud synth passage that needs drama, not sparseness. Classification is on drum rate; the treatment then SCALES with measured loudness.
- **The treatment is the section's own energy curve** (`envelope_palette`): sample the passage's measured RMS, smooth it over ~0.6s, normalise WITHIN the span, and make that the brightness curve. The house then follows the music's contour without marking time. Normalising within the span matters -- against the whole song, a quiet intro renders as a flat dark line.
- **Sparse events are the rhythm there.** Single bass notes and chord changes, thinned to 0.9s apart, each getting a bloom (0.3s in, over a second out) rather than a flash.
- **Placing smooth gestures is only half of it** -- the rhythmic passes run off their own gates and keep flashing underneath. Short hits on the pulse/signature layers are cleared inside ambient passages, plus the flat BASE fill (a constant level under a passage whose point is that the level moves). Motion layers stay: smooth is not empty. Staged drops are exempt, because a quiet passage often ends on one.
- Measured, brightness correlation with music energy inside those passages: Harmony's 90s intro **+0.02 -> +0.24** (it previously had no relationship to the music at all), Cruise +0.39 -> +0.48, This Version of You +0.59 -> +0.63.

**Round 22, three process traps worth remembering:**
1. **The pulse-curve rebuild pass ate the envelope, again.** It had already destroyed the drop/fade envelope; the ambient envelope hit the identical bug because only `_cycle_ids` was exempt. **Any pass that rewrites a shared attribute needs an exemption list that new features get added to, or every future shape will be silently overwritten.**
2. **`lit_frac` is nearly blind to a brightness envelope** -- it counts pixels over a threshold, so modulating brightness barely moves it. Measuring the effect of a brightness curve requires MEAN LEVEL. The first measurement showed "no change" and the code was fine.
3. **A shaped layer over an unshaped floor does not move the floor.** Applying the envelope to 10 big canvases out of several hundred targets moved the correlation by 0.01. Same shape of error as the drop/fade fade.

**No usable drums is not a reason to impose a grid.** This Version of You has EIGHT kick onsets and no detected snare, and the "no usable kick" fallback sent it to QUARTER -- the most rigid mode in the generator, on the least rhythmic track in the library. Where there are no drums, the bass is the pulse. Also added `PULSE_MODE_OVERRIDE` for Meridian: it measures as a steady four-on-the-floor (93% coverage, evenly spaced) and is heard otherwise, because the kick keeps stopping; no rule flipped it without also flipping Fara and 12 to 12, so it is recorded as an explicit taste call.

**File size / effect count:** a full song (241s, 235 models, ambient bed + signature layer) landed at ~52k effect placements / 4.7MB — noticeably bigger than the original flawed attempt (1.8MB) but not unreasonable for a complex real sequence. Not a warning sign by itself.
