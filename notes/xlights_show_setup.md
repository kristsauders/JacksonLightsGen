Krists is building a new 2026 Christmas light show iteratively in Claude Code, one song sequence at a time. This is a multi-session project — expect to come back to this repeatedly across many songs, not just Gooey.

**Key locations:**
- Show folder: `/Volumes/XLIGHTS/XLights 2026` — 235 models (`list_models` via the MCP tool, or parse `xlights_rgbeffects.xml` directly). xLights.app is installed locally (`/Applications/xLights.app`) so Krists reviews sequences visually there; I cannot preview a light show myself.
- MCP server source: `/Users/kristsauders/xlights-mcp-server` (github project by JohnBreault, cloned locally, editable venv at `.venv`). Real audio analysis (librosa/madmom/demucs/whisper), not a stub.
- Reusable scripts: `/Users/kristsauders/xlights-mcp-server/custom_tools/` — all take a `SongName` argument and work across songs. **Pipeline per song: `run_analysis.py <Song>` → `detect_cues.py <Song>` → `generate_song.py <Song> [--out "<Song> (vN).xsq"]` → `verify_sequence.py "<Song> (vN).xsq"` → `verify_render.py "<Song> (vN).xsq"`.**
- **`verify_render.py` is the ground-truth step and must not be skipped** (added 2026-08-09). It drives the xLights CLI (`/Applications/xLights.app/Contents/MacOS/xLights -s <show> -r <seq>`) to render headlessly, then reads the resulting `.fseq` back as real pixel values via `fseq_reader.py` and reports lit fraction and how much of the lit output is saturated red. Everything else in the pipeline only inspects what we *asked* xLights to do; this measures what it actually produced. It is what finally caught the palette bug that four rounds of `.xsq` inspection missed. Related: `isf_shader.py` (builds correct xLights Shader settings from a `.fs` file's own ISF header) and `xLights --shadertranslate` (validates every shader compiles on this Mac). `extract_layout.py` is show-wide and only needs re-running when the layout changes. Analysis helpers: `study_sequences.py`, `deep_dive_sequence.py`, `extract_vocab.py`. (The old per-model `generate_gooey.py` was deleted — `generate_song.py` supersedes it; see [[xlights_human_sequence_patterns]] for why the architecture changed.)
- **`verify_beat_lock.py` is the third verifier (added 2026-08-11) and answers the question the other two structurally cannot: does the light have a RHYTHMIC relationship to the music?** `verify_sequence.py` checks what we asked for, `verify_render.py` checks aggregate colour; a sequence can pass both while being perfectly static against the beat, and for several rounds it was. Reports (a) **beat-lock ratio** — brightness within ±60ms of a detected beat over off-beat brightness, where 1.00 means no relationship at all, and (b) **run-up dip** — lit fraction in the last beat before a section boundary over the preceding seven beats. Post-fix Gooey reference: whole display 1.10, Mega Tree 1.18, dip median 0.73 on 39/56 approaches. Anything sitting at 1.00 ±0.02 is a bug, not a taste call. Wired into `batch_build.sh`, which also now auto-picks each song's next free version number instead of always writing `(v1)`.
- **`plan_song.py` is the PLANNING step, run before generating anything** (added 2026-08-11). Krists asked directly whether I was "weighing in rather than purely automating it"; the honest answer was that the generator is a rule system and nothing is per-song. This tool exists for the other half: one screen per song showing measured loudness rank per section (NOT the detector's label — labels are wrong often enough to matter), which voices are actually playing with their **repetition score**, every drop/dropout/riser, and a list of **judgement flags** for places the rules will likely get wrong. Flags that have already earned their keep: "labelled CHORUS but kick density 0.00 — likely a breakdown", "sparse, NO repeating figure, risks looking empty", "climax spans §N-§M, treat as ONE peak". Read the flags, decide, then generate. Note it reads RAW `analysis.json` sections while the generator merges at runtime, so a song with many slivers (Gooey: 47 of 57 sections under 2 bars, unique to that track) looks worse in the plan than in the sequence.
- Generated data per song (JSON caches, cue sheets): `/Volumes/XLIGHTS/XLights 2026/.generation/<SongName>/` (analysis.json, cues.json, cuesheet.md) plus a show-wide `.generation/layout.json`. This lives on the XLIGHTS volume, not in scratchpad, so it survives across sessions.
- Demucs stem separation output caches to `<show folder>/stems/<SongName>/` automatically (vocals/drums/bass/other .wav) — re-running analysis on the same song skips the expensive separation step.

**Architecture decision — why we don't use the MCP server's built-in `create_sequence` "auto" mode:**
`engine.py`'s auto-generation is a fixed rule table (model type -> effect list, energy threshold -> layer), seeded only by `random.Random(hash(song_name))`. It produces valid, competent output but the same "recipe" for every song — no actual musical listening. Instead: use the MCP server's audio-analysis tools/library code (real value, expensive to redo), but write a fresh, song-specific Python script per song that does its own musical listening (melody detection, risers, drop anticipation, etc.) and places effects directly via `xsq_writer.write_xsq`. Reuse `engine.py`'s data tables (`EFFECT_VARIANTS`, `BED_EFFECTS`, `MOTION_EFFECTS`, `STEM_MOTION_OVERRIDES`, etc.) and helpers (`_detect_model_groups`, `_get_settings`, `_effect_name_from_key`) by importing them for the ambient "bed" layer — no need to reinvent validated effect presets — but write the creative/signature-moment logic fresh each time.

**Multi-song status (2026-08-09):** the pipeline was validated on a second song, `Too Slow (All Night)` (Eliza Rose & Oppidan, house), converted from a freshly-exported FLAC. Ran end-to-end with **zero song-specific code changes** — `run_analysis.py`/`detect_cues.py`/`generate_song.py`/`verify_sequence.py` all just take the song name as an argument. Structural fixes transferred perfectly (window matrix trio: 108/108/108 effects, exact match; no stale targets; garage curtain mostly symmetric). One thing that did *not* transfer cleanly: density ran hot (45% lit fraction vs. Gooey's ~35-40%, both above the 11-26% human range) — this track's energy profile sits higher/more consistently than Gooey's (house music pumps more steadily; Gooey had bigger quiet-loud swings), and the `n_active_target` energy bands in `generate_song.py` are absolute thresholds tuned against Gooey's specific energy distribution, not normalized per-song. Worth watching if this becomes a recurring pattern across songs — the fix would be percentile-based energy classification within each song rather than fixed absolute thresholds, but not worth doing speculatively before seeing whether it actually reads as too busy in practice. See [[xlights_human_sequence_patterns]] for the density benchmark this is measured against.

New song folders exported as FLAC (converted to MP3 at the show root, matching `Gooey.mp3`'s convention, track-number prefixes stripped): `Too Slow (All Night).mp3`, `The WhatsApp Shakespeare.mp3` (RAYE), `12 to 12.mp3` (sombr) — the last one converted but not yet sequenced.

**Sequenced so far:** `Gooey` (v8), `Too Slow (All Night)` (v8), `The WhatsApp Shakespeare` (v2 — the one Krists said "turned out really great" was the round before this one), `12 to 12` (v1, sombr). Treat that as the expected baseline; if a new song needs structural fixes, that's a signal about a real generator (or shared library) gap rather than normal per-song work.

**Song set as of 2026-08-11 (11 sequenced):** Gooey, Too Slow (All Night), The WhatsApp Shakespeare, 12 to 12, World Is Mine, Aperture, Fara, Lose My Cool, So Easy (To Fall in Love), The Ambition (Girls Trip), ENIGMA (LSZEE, added 2026-08-11 from `1-08 ENIGMA.flac`, 3:33). New songs arrive as FLAC in the show root; convert with `ffmpeg -i "<file>.flac" -codec:a libmp3lame -q:a 0 "<Song>.mp3"` at the show root (strip track-number prefixes), then run `batch_build.sh "<Song>"`, which auto-picks the next free version number.

**Shader tooling in `custom_tools/` (added 2026-08-16).** The shader library lives in `<show>/Shaders/` — 44 files, 32 written for this show. Three tools, all of which render and measure rather than inspect source, because reading GLSL has repeatedly missed real breakage:
- `shader_smoke_test.py [names...]` — **the gate for any new or edited shader.** Renders each for 8s on Garage Roof (the largest plain 2D canvas; never Fence Matrix 1, which is rotated front-to-back) and reports lit / spatial variance / motion / flicker. Catches the three failure modes that have all shipped past a careful read: compile error (renders BLACK, silently), compiles-but-static, and washed-out. It found two shaders that had been placed in songs for days doing nothing visible — Ember Swarm's embers were ~1% of the canvas across, Pulse Rings' rings were thinner than the measured pixel spacing. Note `xLights --shadertranslate` is NOT usable: it takes a directory and reports "0 .fs found" against this show's Shaders folder.
- `shader_palette_test.py [names...]` — renders shaders with one deliberately hue-spread palette, alone on the prop, so hue counts are attributable. Sampling a real song cannot answer colour questions: shaders there sit under other layers and each carries a different palette.
- `colorize_shaders.py [--apply]` — the greyscale→palette conversion. Originals in `Shaders/_greyscale_backup/`; reverting is a file copy.

**Analysis modules in `custom_tools/` (all cache to `.generation/<Song>/`):**
- `instrument_voices.py` — band-split drum voices (kick/snare/hat) + bass/chord/vocal, drum-fill detection, pitch-mapped melody extraction.
- `harmony.py` (added 2026-08-10) — `madmom` key detection + chord timeline. Key is RELIABLE (measured confidence 0.89-0.95 on three of four songs; `12 to 12` only 0.54, so gate on confidence). Chord richness varies enormously by genre: WhatsApp Shakespeare 82 segments, `12 to 12` 91, Gooey only 60 with a single 54-second block — chord recognition is weak on electronic/modal material, so chord CHANGES are a good boundary signal on harmonic songs and near-useless on others. Caches `harmony.json`. Note: all four songs so far are MINOR, so a key→palette mapping driven mainly by mode gives less cross-song variety than the existing random-family pick — worth weighing before wiring it in.
- `lyrics.py` (added 2026-08-10) — Whisper word timestamps on the demucs VOCALS stem. Caches only the transcription (`lyrics.json`), recomputing derived hook/phrases each call so heuristics can be re-tuned without re-running Whisper (~30s/track with the `base` model).

**Two measured limits of the lyrics work, don't re-learn these:**
1. **Whisper cannot tell you where singing stops.** 90% of consecutive word gaps came back as exactly 0.00s on sung material, so gap-based phrase splitting produced a single 56-SECOND "phrase". Phrases are now derived from the VOCAL STEM'S RMS ENERGY instead (45 sensible phrases on the same track). Word TIMINGS are usable; word-gap silence is not.
2. **Hook detection from sung vocals is unreliable.** Content words are sparse and mis-heard (mean word confidence 0.62); the first attempt returned the pronoun "her" as the song's hook. With a stricter filter it now correctly returns "none found" rather than something wrong. Treat any hook result as best-effort and always gate it.

**`12 to 12` needed a real shared-library fix, not a per-song one**: `src/xlights_mcp/audio/structure.py`'s song-structure detector collapsed the whole 243s song into one section because its "found enough boundaries" fallback check counted boundaries without checking their DISTRIBUTION — see the round 14 entry in [[xlights_human_sequence_patterns]] for the fix and for why this song's resulting near-uniform "chorus" labelling turned out to be an honest description of the audio (very low RMS dynamic range throughout, confirmed by direct measurement) rather than a second bug. This file (`structure.py`) is shared MCP server code, not part of `custom_tools/` — a fix there benefits every song, past and future, not just the one that surfaced it.
